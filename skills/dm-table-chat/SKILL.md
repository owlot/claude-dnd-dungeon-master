The table chat (`.claude/tools/table-chat/`, README there) is a server that takes the players' spoken lines from a tablet, drafts the NPC's reply with the local model, speaks the approved reply in the NPC's voice, and writes the NPC log and the NPC memory files itself. This skill is how Claude drives it, through `.claude/tools/table-chat/table_chat.py` (`python .claude/tools/table-chat/table_chat.py help` lists every command). Everything the DM page can do, Claude can do; the DM still decides what is said.

**This replaces the `conversation-npc` agents for the conversation it runs.** Do not also spawn or message `npc-[slug]` agents for it, do not append to its NPC log by hand, and do not write the NPC memory file: the server does all three. (Use one engine per conversation. When the table chat is not running, the normal warm-agent flow in CLAUDE.md applies.)

**Tools or command line.** If the `table-chat` MCP server is connected (tools named `table_chat_*`, registered in `.mcp.json`), call those tools; every command below has a tool of the same name (`approve` is `table_chat_approve`, `room add` is `table_chat_room` with `action: add`, and so on) and returns the same text. If the tools are not available, use the command line as written. The event watcher is always `table_chat.py watch` through the Monitor tool, because tools cannot push events.

## Before the first conversation

1. The server must be running on the DM's machine (`.claude/tools/table-chat/run.sh`). Check with `python .claude/tools/table-chat/table_chat.py status`. If it cannot be reached, tell the DM to start it and stop here. Set `TABLE_CHAT_PORT` if the DM runs it on another port.
2. Start **one** persistent watcher for the whole session with the Monitor tool: `python .claude/tools/table-chat/table_chat.py watch`. It prints one line per event and reconnects when the server restarts. Lines you will see: `PARTY LINE:` (a line from the tablet or the DM), `DRAFT READY:` (a drafted reply, narration or speak-up waiting for approval), `NEED:`, `DRAFT FAILED:`, `SPOKEN:` (an approved line was spoken), `CONVERSATION:` (room or addressee changed, or none active).

## Starting a conversation

1. Run `/dm-checkpoint-log [campaign]` first (CLAUDE.md requires it before every named-NPC conversation). If nothing in-game has been said in this context since the last flush (a tooling session, for instance), say so in one line and skip the write.
2. `table_chat.py prepare <npc-slug>` shows what the server worked out from `party/state.md` and the NPC's own files: where, the scene, who else is there (only NPCs the state places with this NPC; empty when it says nothing) and how each NPC refers to each person. Show the DM a short summary: place, who is in the room, any label that uses a real name for someone the NPC may not know. **The DM confirms or corrects** (place, room, scene text, labels). A prefilled place is blank when the state does not place the NPC: ask.
3. Third-party leaks follow `.claude/rules/npc-memory.md`: if the NPC could plausibly know something from someone else, propose it to the DM; only an approved leak goes into the scene text, as a plain sentence after the surroundings ("Vajra told you earlier that ..."). The scene is the only channel to the NPC besides its files.
4. `table_chat.py start <npc-slug> [--others a,b] [--location "..."] [--scene "..."]`. Change a label with `labels <viewer> <key> "how <viewer> refers to <key>"` (before or during).
5. Tell the DM the conversation is live and that the party picks who is speaking on the tablet. Then wait for events.

## Running it

**Rules learned the hard way**
- **Look it up before you cue it.** Before narrating or cueing anything about an item, someone's equipment or a place, read the character sheet (`party/characters/`), the object ledger (`party/objects/`) and `party/state.md`. If more than one thing fits ("a ring" when he carries three), ask the DM which. Never let a model pick.
- **Give facts up front, only when the NPC would know them.** Before narrating or cueing, you may `tell` an NPC a fact, but only after you have established that it should have it: (a) it can perceive it now (a visible look, material or size of something in front of it, someone it can see), (b) its own files or memory say so, or (c) the DM ruled it. You must state that basis: `tell room "<what everyone present can see>" --because "<why>"` or `tell <npc-slug> "<fact>" --because "<why>"`; add `--remember` for knowledge it should keep. The basis is logged with the fact as `*[DM fact ... (basis: ...)]*`. Never tell an NPC what it could not know: an item's provenance, its magic, its value as the party learned it, a secret, or anything the party did elsewhere. For those, let the NPC play ignorance or send a NEED, and put a third-party fact in only when the DM approves the leak. If you cannot name a basis, do not tell it.
- **Handing over an object: `give`.** When something changes hands, run `give <npc-slug|room> <object-slug>` (or `table_chat_give`) before narrating: it tells the NPC only what can be seen of the object, taken from `party/objects/<slug>.md`, and leaves out history, origin, value and magic. If the object has no ledger entry or the entry has no physical look, it fails and asks: get the look from the sheet or the DM and pass `--look "..."`. Check which object it is first (the sheet may list several of the same kind).
- **Do not show a draft with a known invention.** If a draft invents a fact (a material, an age, a place, where someone is), `redraft --direction "..."` with what is true and what to leave out, and show the DM the clean version. Show the invented one only if redrafting failed, and say so. `--direction` works for NPC replies (speak-ups) as well as narration.
- **Use the event text.** `DRAFT READY` already carries the whole draft: read it from the event instead of polling `status`.
- **Plain buttons.** No shorthand ("stray comma", "misses X"). One idea per line; each option says what it does. If the DM answers with a message instead of a button, read the message as the answer.
- **Never start a second server on the live instance.** Test servers use their own port (they keep their own state and audio files); the live conversation's state file is not to be touched.

- **Approval is a button question (AskUserQuestion), built to be scanned in two seconds.** Put the reading aids in the question itself, not just in the text above it: a header naming the speaker, a question that is a one-line gist of the draft (what the NPC does or says in about 15 words, plus a flag for anything in it the files do not support or that gives something away: "reveals X", "invents Y", "asks for a roll"), and options Approve / Draft again / No reply (plus a useful alternative when there is one, such as "Edit"). Show the full text of the draft in the message before the question so the DM can read it when the gist is not enough. If the DM answers with a message instead of choosing, read the message as the answer; if none arrives, ask once to resend.
- **On `DRAFT READY` for a party line**: show the DM, in this order, what the party said, who it was said to, and the drafted reply, then ask one thing: approve, edit, redraft, or no reply. Follow the NPC presentation rules in `dm-narration-format`: add a `[DM: ...]` note when the draft carries information the party should not get unchecked, or a roll is warranted (name the roll as in "Roll Prompts": ability, skill, DC, modifier) and **wait for the DM's roll result before approving**.
  - Approve as drafted: `table_chat.py approve`. DM edit: `table_chat.py approve "the exact text"` (the DM's wording is final; fix spelling of names in the DM's text only if clearly a typo).
  - `redraft` (optionally `--party "fixed transcription"`, `--to <npc>` to hand the line to someone else in the room), `skip` for no reply.
  - Never approve without the DM's go-ahead, unless the DM has said to auto-approve for this conversation. Even then show each line right after it is spoken.
- **Mistranscribed line**: tell the DM, offer `redraft --party "..."` with the fixed line before approving.
- **`NEED`**: the NPC should know a fact the files do not give. Answer from the campaign files (run `python .claude/scripts/npc_links.py [campaign] [slug] --people [x]`, the ledgers, `party/relationships.md`, other NPCs' memory) or ask the DM, then `table_chat.py answer "the fact"`. If the NPC would not know it: `answer --unknown`. A lasting answer is saved to the NPC's memory when the conversation ends.
- **Who the party addresses**: when the DM says the party turns to someone ("they ask Dagna"), `address <npc-slug>`. For someone speaking up unprompted: `chime <npc-slug>`.
- **People leaving and arriving**: `room remove <slug>` / `room add <slug>`. A returning NPC remembers what it heard before leaving; narrate what it missed. A newcomer hears only what comes after. While nobody is in the room party lines are refused: narrate until someone returns.
- **Narration between the lines** (a pause, someone leaving, coming back, the room reacting): `narrate "direction"` (empty direction for a natural small beat), show the draft, approve as above. Narration is heard by every NPC present, shown on the tablet and spoken in the narrator's voice.
- **Actions are narration, never a party line.** When the DM says a character does something ("Corrin gives Embric the ring", "Caelith draws his sword"), use `narrate` with that as the direction, approve it, and then `chime` the NPC with a cue for how they react. `say` is only for words a character speaks. If a `say` line went out by mistake, `withdraw` it (nothing is logged) and redo it properly.
- **A line the DM types** instead of the tablet: `say <speaker-slug|party> "text"`.
- `stop` silences the tablet; `restart` starts the same conversation over (log cut back to its header, nothing saved).
- After a significant decision, offer 2–3 consequence suggestions as in CLAUDE.md. Prompt the DM at the end of every message.

## Ending

1. `table_chat.py end` drafts each NPC's closing record from what that NPC heard and saves it: the `## Conversation End` block (one per NPC in the room) into the NPC log and a `### Session N` entry into each NPC's memory file. If it prints `NOT SAVED`, read the drafts with the DM, fix them, write them to a JSON file and run `end --confirm file.json`. `end --review` prints drafts without saving; `discard [--delete-log]` ends without saving.
2. Report the saved log and memory paths. Then update `party/state.md` and the ledgers as usual for what changed (location, relationships, objects); the closing record is the NPC's view, not the campaign's.
3. The session conversation log (`/dm-checkpoint-log`) still covers what was said in the main thread; the NPC log written by the server is the NPC conversation archive.
